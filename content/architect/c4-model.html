The C4 model

Four levels of zoom over one system, plus a supplementary set. All seven are on this page. Three are filed elsewhere — you reach for a sequence or deployment diagram by the job it does rather than because C4 names it — so their entries live in those categories and are shown here too. C4 is a notation, not a methodology: use the levels you need and stop, which for most systems is the first two.

System context diagram (C4 level 1)

C4 model

The whole system as a single box, surrounded by every person and external system that touches it. C4 adopted it as level 1, but the context diagram is older than C4 and stands on its own — it is the only architecture diagram a non-technical audience should ever be shown. Nothing inside the box is named beyond the system itself: no technology, no internal service, nothing that assumes the reader already knows how the thing works. Its discipline is almost entirely in what it refuses to include, which is exactly why it survives unchanged from the first kickoff meeting to the last steering committee. In notation terms it is deliberately impoverished: one shape for the system, one for a person, one for an external system, and a labelled arrow between them — there is no room in that vocabulary to smuggle in an implementation detail even if you wanted to. Simon Brown's C4 model borrowed it wholesale from older context-diagram traditions (structured analysis, DFDs) precisely because it already worked; C4's contribution was giving it a fixed place in a zoom sequence. Expect to redraw it the first week of a project and then barely touch it again — its stability is itself a signal that the team agrees on what the system is for.

Container diagram (C4 level 2)

C4 model

The deployable units inside your system — applications, services, databases, brokers — and the technology each one is built on. This is the default answer to “explain the architecture”. Every box on it is something that actually runs and could, in principle, fail independently of the others, which is what separates a container from a mere concept or a component. It is drawn once per system, kept current as the honest source of truth, and is usually the single diagram new engineers are shown before they are given repository access. Each box names a real, independently deployable thing and the technology it runs on — “Order API, ASP.NET Core” rather than “backend” — because vague boxes are how a container diagram quietly turns into a context diagram with more shapes. Arrows between containers should carry a protocol (REST, gRPC, AMQP) and, where it matters, a synchronous-versus-asynchronous distinction, since that is usually the detail a reviewer is actually trying to extract from the picture. It is also the first diagram most incident channels paste in, because it is the smallest picture that still shows which deployable thing to restart.

Component diagram (C4 level 3)

C4 model

One container opened up: the major structural parts inside a single service and the responsibilities they hold. Worth drawing only for a service whose internals are genuinely non-obvious — most services do not earn one, and forcing it produces a picture nobody consults again. It sits between the container diagram, which a whole team owns, and the code itself, which one engineer owns, so it is usually drawn by whoever is about to make a change that crosses more than one internal boundary and wants a second opinion before they do. Each component here should map to a real seam in the code — a namespace, a package, an assembly — not an aspirational one; a component diagram that draws boundaries the codebase doesn't actually respect is a wish list, not a picture of the system. It tends to go stale faster than the levels above and below it, because internal refactors that never touch an external contract are exactly the changes nobody remembers to reflect here, so treat any copy older than a couple of sprints as suspect.

Code diagram (C4 level 4)

C4 model

The innermost C4 ring: the classes and interfaces inside one component. The level the C4 model itself tells you to skip most of the time, on the grounds that an IDE can generate a more accurate one on demand than a human can maintain by hand. The rare case worth drawing by hand is a design conversation about a pattern — a specific set of interfaces and their relationships — before the code exists to generate the picture from. When it is worth drawing, it is usually to settle a naming or responsibility argument about a pattern — visitor versus strategy, where a factory sits — before the classes exist to generate the picture from automatically. Once the code exists, regenerate it from the source rather than hand-maintain it; a hand-drawn class diagram that has drifted from the actual signatures is worse than no diagram, because it actively misleads the next reader instead of leaving them to check the source.

System landscape diagram

Architecture & system-level also shown here

Every system in the organisation on one page, grouped by domain, each marked with who owns it and whether it is being invested in, tolerated or retired. It is a context diagram scaled up from one system to all of them, and its main enemy is scope creep: past a few dozen boxes it stops being readable and starts being decorative. Its real audience is whoever is deciding where the next quarter of engineering investment goes, not whoever is building any one box on it. Colour or shading by investment status (invest, tolerate, retire) is what turns the picture from an inventory into a decision tool — without it, the diagram just confirms that a lot of systems exist, which nobody doubted. It is usually maintained by an enterprise or platform architecture function rather than any single delivery team, updated on a quarterly cadence rather than per release, and its main enemy besides scope is staleness: a landscape diagram that still shows a decommissioned system as active has stopped being trusted the moment someone notices.

Sequence diagram

Interaction & runtime also shown here

Participants across the top, time running down, messages between them in order. For distributed systems this is the highest-value diagram there is — structure diagrams show what exists, this shows what happens. It is the only diagram most teams reach for during an incident, because it is the one that can show a call arriving late, a retry firing, or a response coming back from the wrong participant. Keep it to one scenario at a time; a sequence diagram that tries to show the happy path and every error branch on the same sheet stops being readable exactly when you need it most. Lifelines run down the page from each participant, activation bars show when a participant is actually doing work versus waiting, and a return arrow (often dashed) closes the loop — all three matter when the question is where time is actually being spent, not just who calls whom. Alt and opt fragments can express a branch or an optional step without needing a second diagram, but resist the temptation to model every edge case in one sequence diagram; past two or three branches, split the error paths into their own sheet rather than let the happy path drown in boxes.

Deployment diagram

Deployment & infrastructure also shown here

Where the software actually runs: regions, availability zones, nodes, instance counts, and the replication between data stores. Where availability and cost arguments are finally settled, because it is the diagram that turns an availability target into an arithmetic problem — how many nodes, in how many zones, replicated how, at what utilisation. Executives approve the container diagram in principle; they approve the bill implied by this one, so it is worth drawing with real instance types and real counts rather than placeholder boxes. UML gives it formal notation — nodes for physical or virtual hosts, nested nodes for what runs inside them, artifacts for the deployed units — but in practice most teams draw a looser, C4-flavoured version with cloud-provider icons, which is fine as long as zone boundaries, replication direction and rough capacity numbers survive the simplification. The diagram's job is to make a redundancy claim checkable by inspection: if you can't point at the picture and show which single box, once removed, would take the system down, the deployment diagram hasn't actually been drawn yet.
