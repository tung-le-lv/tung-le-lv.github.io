The C4 model

Four levels of zoom over one system, plus a supplementary set of three. Each of the four core levels has its own article, linked below. The three supplementary ones are filed elsewhere — you reach for a sequence or deployment diagram by the job it does rather than because C4 names it — so their entries live in those categories and are shown here too. Underneath the four core levels sits a fixed hierarchy: a software system is made up of one or more containers, each of which contains one or more components, which are in turn implemented by one or more code elements — and it is people who use the software systems you build, not the other way round. Simon Brown frames the zoom sequence itself as Shneiderman's mantra — overview first, zoom and filter, details on demand — which is why each level exists to answer a narrower question than the one before it. C4 is a notation, not a methodology: use the levels you need and stop, which for most systems is the first two. Brown's own guidance is blunter still — every software system should have a context and a container diagram; component and code stay optional, worth drawing only where the cost of keeping them current is repaid by the confusion they prevent.

System landscape diagram

Architecture & system-level also shown here

Every system in the organisation on one page, grouped by domain, each marked with who owns it and whether it is being invested in, tolerated or retired. It is a context diagram scaled up from one system to all of them, and its main enemy is scope creep: past a few dozen boxes it stops being readable and starts being decorative. Its real audience is whoever is deciding where the next quarter of engineering investment goes, not whoever is building any one box on it. Colour or shading by investment status (invest, tolerate, retire) is what turns the picture from an inventory into a decision tool — without it, the diagram just confirms that a lot of systems exist, which nobody doubted. It is usually maintained by an enterprise or platform architecture function rather than any single delivery team, updated on a quarterly cadence rather than per release, and its main enemy besides scope is staleness: a landscape diagram that still shows a decommissioned system as active has stopped being trusted the moment someone notices.

Sequence diagram

Interaction & runtime also shown here

Participants across the top, time running down, messages between them in order. For distributed systems this is the highest-value diagram there is — structure diagrams show what exists, this shows what happens. It is the only diagram most teams reach for during an incident, because it is the one that can show a call arriving late, a retry firing, or a response coming back from the wrong participant. Keep it to one scenario at a time; a sequence diagram that tries to show the happy path and every error branch on the same sheet stops being readable exactly when you need it most. Lifelines run down the page from each participant, activation bars show when a participant is actually doing work versus waiting, and a return arrow (often dashed) closes the loop — all three matter when the question is where time is actually being spent, not just who calls whom. Alt and opt fragments can express a branch or an optional step without needing a second diagram, but resist the temptation to model every edge case in one sequence diagram; past two or three branches, split the error paths into their own sheet rather than let the happy path drown in boxes.

Any flow with three or more participants. Auth, checkout, saga steps, retries, incident reconstruction.
It must show
Timeouts and retries on network hops, idempotency keys, and at least the declined and timed-out branches.
Common failure
Happy path only. And treating a timeout as a decline — on a timeout you do not know whether it happened.

Deployment diagram

Deployment & infrastructure also shown here

Where the software actually runs: regions, availability zones, nodes, instance counts, and the replication between data stores. Where availability and cost arguments are finally settled, because it is the diagram that turns an availability target into an arithmetic problem — how many nodes, in how many zones, replicated how, at what utilisation. Executives approve the container diagram in principle; they approve the bill implied by this one, so it is worth drawing with real instance types and real counts rather than placeholder boxes. UML gives it formal notation — nodes for physical or virtual hosts, nested nodes for what runs inside them, artifacts for the deployed units — but in practice most teams draw a looser, C4-flavoured version with cloud-provider icons, which is fine as long as zone boundaries, replication direction and rough capacity numbers survive the simplification. The diagram's job is to make a redundancy claim checkable by inspection: if you can't point at the picture and show which single box, once removed, would take the system down, the deployment diagram hasn't actually been drawn yet.

Where does everything run, and what survives when part of it dies?
Reach for it when
Every production design, and every conversation about an SLA.
It must show
Zone and region boundaries, replication direction and mode, where state lives, and rough instance counts.
Common failure
Omitting availability zones. Without them the diagram cannot answer a single HA question.
