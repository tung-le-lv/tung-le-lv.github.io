Start here · how often a software architect actually draws each one

Ranked from a software architect’s chair — the diagrams you are expected to produce, to read in review, and to defend. A BA, a UX designer or an SRE would order the same 110 types very differently, and each would be right about their own job.

The everyday five

Know these cold. Between them they answer most of the questions you will be asked, and you should be able to draw all five from memory.

  • C4 — context, container, component, code — The default way to explain a system top-down, one audience per level. If you master one thing here make it this — and note that in practice you draw the first two levels and stop.
  • Sequence diagram — Who calls whom, in what order, and what happens when a step times out. The one to reach for in a design review and again in the post-mortem.
  • Deployment diagram — What runs where: regions, availability zones, instance counts, replication mode. Where availability and cost arguments are actually settled.
  • Entity relationship diagram (ERD) — Keys, attributes, and the cardinality that quietly encodes the real business rules.
  • State machine diagram — The lifecycle of an order, payment, job or subscription. Drawing one surfaces the illegal transition nobody had thought about.

Architecture and design thinking

Fewer boxes, more consequence. These are the ones that change what gets built rather than describing what already exists.

  • Bounded context map (DDD) — Where the seams between systems and teams fall. Essential before splitting a monolith, and largely academic afterwards.
  • Domain model — Aggregates, entities and value objects — and the invariants each aggregate is responsible for.
  • Event storming board — Events, commands and policies on a wall with the business in the room. The deliverable is the boundaries you find, not the wall.
  • Data flow diagram (DFD) — The canvas a STRIDE threat model is drawn on. The trust boundaries matter far more than the processes.

Ops, data and process

Drawn by whoever owns the consequence — which, more often than anyone expects, is the architect.

  • Network / VPC diagram — Subnets, routing, ports and peering: what is actually reachable from where.
  • CI/CD pipeline diagram — Build, test, promote, and the gate at each step. One artefact, never rebuilt per environment.
  • Data pipeline / ETL–ELT — Sources, transforms, sinks — and the backfill route for the day a transform was wrong.
  • Data lineage diagram — Where the number on the report came from. Designed the day the pipeline is designed, not the day the auditor asks.
  • BPMN — When the business owns the process and a workflow engine executes the model itself.
  • Flowchart — One actor, sequential steps, unambiguous branches. Still the right answer more often than its reputation suggests.
  • Business capability map — What the business does, shaded by how well each capability is served. Enterprise-architect territory, and the fastest way to make a funding case.
  • Value stream map — Where the time actually goes — and it is almost never inside the work.

UML you will still meet in the wild

A handful earn their keep. The rest are worth recognising so you know what you are holding when someone hands you one.

  • Class diagram — A domain model or a library’s internals, where cardinality and ownership carry real content.
  • Component diagram (UML) — Modules with the interfaces they provide and require. Not the C4 component diagram — same word, different diagram, and worth saying which you mean before anyone draws.
  • Activity diagram — A process with genuine concurrency: fork, join, and branches that must all complete. If there are no bars on it, you wanted a flowchart or a swimlane.
  • Package diagram — Layering and dependency direction — and the only one on this list you can assert in a build test.
  • Use case diagram — Actors and scope, for stakeholder alignment. Deliberately silent about how anything works.
  • Object diagram · Communication diagram · Timing diagram · Composite structure diagram · Profile diagram — Rarely. Recognise them; you will read one far more often than you will draw one.

Where you meet product and design

You will not draw these often, but the decisions made on them land on your side of the line permanently.

  • User flow & screen-to-API map — Product owns the screen flow; you own the row underneath it that says which service owns each field. That row is where API shape gets decided, and it is worth being in the room for.
  • Wireframes and visual design — Genuinely not yours, and the one place on this list to defer — but read them closely enough to spot the screen that quietly needs four services to render.

A practical bar. C4 plus sequence, deployment, ERD and state machine cover roughly nine architecture conversations out of ten. Everything else here you should be able to recognise and read; you will draw it occasionally at best — which is exactly what a dictionary is for.
