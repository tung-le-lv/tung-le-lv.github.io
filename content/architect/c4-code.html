C4 model

The innermost C4 ring: the classes and interfaces inside one component. The level the C4 model itself tells you to skip most of the time, on the grounds that an IDE can generate a more accurate one on demand than a human can maintain by hand. The rare case worth drawing by hand is a design conversation about a pattern — visitor versus strategy, where a factory sits — before the classes exist to generate the picture from automatically, or as a reusable template for a pattern that recurs identically across several components in the same codebase. Once the code exists, regenerate it from the source rather than hand-maintain it; a hand-drawn class diagram that has drifted from the actual signatures is worse than no diagram, because it actively misleads the next reader instead of leaving them to check the source.

Intent

The intent of a code-level diagram is narrow and specific: illustrate the structure of the code that implements one component.

Structure

If you're working in an object-oriented language, a UML class diagram is the usual choice, generated automatically from the code or sketched by hand. Whichever way you produce it, the danger is the same — it is trivially easy to include every field, every property, every method, especially if a tool is generating it for you, and the result is a diagram nobody can hold in their head. Include only what the specific story you're telling actually needs, and limit its scope deliberately: to the internals of one component, never to an entire application. A class diagram that tries to describe a whole codebase produces the same tangle regardless of how well-structured the code underneath it actually is.

Motivation

This is the level that finally bridges the coarse-grained, architectural view of the system and the real code a developer opens in an IDE. Its only job is to make that bridge visible when it isn't obvious from the component diagram alone.

Audience & required or optional

Developers, specifically — nobody else has a reason to read this level. It's also the level the C4 model itself tells you to treat as optional, and generally skip: this detail already lives in the code, and any modern IDE can generate a more accurate version of it on demand than a person can keep up to date by hand. The cases worth an exception are a design conversation about a specific pattern — visitor versus strategy, where a factory should sit — before the classes exist to generate the picture from automatically, or a reusable template for a pattern that recurs identically across several components in the same codebase.

Common pitfalls

  • Checking it in as documentation. A hand-maintained class diagram is wrong within a sprint, and a diagram that's wrong is worse than no diagram, because it actively misleads the next person who trusts it instead of sending them to the source.
  • Generating it for an entire application instead of one component. Auto-generation tools will happily produce this; the resulting diagram is unreadable regardless of how clean the underlying code is.
  • Including every attribute and method because the tool makes it easy. Keep only what the specific narrative you're building actually needs.
