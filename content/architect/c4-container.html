C4 model

The deployable units inside your system — applications, services, databases, brokers — and the technology each one is built on. This is the default answer to “explain the architecture”. Every box on it is something that actually runs and could, in principle, fail independently of the others, which is what separates a container from a mere concept or a component. The name predates Docker and does not mean one: Brown picked “container” for anything independently deployable and independently runnable, which excludes a library or a JAR/DLL unless it ships as its own runnable process, and still includes a managed data store like S3 or RDS, because you own the bucket or schema even though somebody else runs the hardware under it. It is drawn once per system, kept current as the honest source of truth, and is usually the single diagram new engineers are shown before they are given repository access. Each box names a real, independently deployable thing and the technology it runs on — “Order API, ASP.NET Core” rather than “backend” — because vague boxes are how a container diagram quietly turns into a context diagram with more shapes. Arrows between containers should carry a protocol (REST, gRPC, AMQP) and, where it matters, a synchronous-versus-asynchronous distinction, since that is usually the detail a reviewer is actually trying to extract from the picture. It is also the first diagram most incident channels paste in, because it is the smallest picture that still shows which deployable thing to restart.

Intent

A container diagram answers five questions: what is the overall shape of the software system, what are the high-level technology decisions, how are responsibilities distributed across it, how do the containers communicate with one another, and — for a developer joining the team — where do I actually need to write code to ship a feature.

Structure

Draw a block diagram of the high-level technical building blocks — the containers — that make up your software system, with a bounding box around all of them corresponding to the single box shown on the system context diagram. This is your zoomed-in view of what was one box a moment ago, and it's usually the diagram people reach for first when they ask how a system actually works.

How much detail you add depends on when you're drawing it. Sketching this during an up-front design exercise, add whatever you know and no more. Documenting a system that already exists, add the finer details — protocols, port numbers — because you have them to hand. What the diagram should never show is the number of physical instances of anything: whether the API sits on one box or a farm of twenty is a deployment diagram's job, not this one.

Elements

A container diagram usually carries three kinds of element.

  • Containers — anything that has to be running for the system to work, and could in principle fail independently of everything else. In practice that covers a wide range of concrete things: a server-side web application (Java/Spring, ASP.NET, Rails, Node), a client-side web application running in the browser (an Angular, React or Vue SPA), a client-side desktop application, a mobile app, a server-side console application or batch process, a microservice, a serverless function, a database schema, a blob or content store, a file system, even a shell script — anything independently deployable and independently runnable. Capture a name, the implementation technology, and a short description of its responsibilities.
  • People and software systems — the same collection shown on the system context diagram, repeated here for continuity, so a reader can follow the story from one diagram to the next without losing their place.

A managed data store like Amazon S3 or RDS still counts as a container, even though you don't run the underlying hardware — you own the bucket or schema, and it's an integral part of the architecture. A JAR file or a DLL does not count, unless it happens to ship as its own runnable process; a container is a runtime construct, not a packaging one. And if a business-critical file system is in play, give it its own container box — log files written incidentally by half your containers usually aren't worth the clutter of showing.

Interactions

Communication between containers is out-of-process almost by definition, so it's worth being precise about how it happens. Annotate each line with:

  • the purpose of the interaction (“reads/writes data from”, “publishes events to”),
  • the communication mechanism (REST, gRPC, JMS, a Windows service call — whatever's actually in use),
  • the communication style (synchronous, asynchronous, batched), and
  • protocols and port numbers where they matter (HTTPS, AMQP, SMTP).

A container diagram with unlabelled arrows is a picture of nouns connected by mystery.

Motivation

Where the context diagram showed your system as one opaque box, the container diagram opens that box up. That earns its keep two ways: it makes the high-level technology choices explicit rather than implicit in someone's head, and it shows how the containers actually talk to each other. It's also the missing middle step between a context diagram — too coarse to be useful for engineering work — and trying to draw every component in the entire system on one page, which is too cluttered to be useful for anything.

Audience & required or optional

Technical people, inside and outside the immediate team — developers, but also the operations and support staff who'll be paged when one of these containers falls over. Like the context diagram, this one isn't optional: every software system should have a container diagram. Unlike the level above it, this is usually the diagram that stays open in a tab during incident response, because it's the smallest picture that still tells you which deployable thing to restart.

Common pitfalls

  • Vague boxes. “Backend” is not a container name; “Order API, ASP.NET Core” is. A diagram that can't be read back as real, independently deployable things has quietly become a context diagram with extra shapes.
  • No technology on the box. If you can't say what it's built on, you probably haven't zoomed in far enough yet to be drawing this diagram.
  • Treating “container” as a synonym for Docker container. The name predates Docker; a container here just means independently deployable and independently runnable, and plenty of containers on a real diagram never see a Dockerfile.
  • Showing physical deployment detail — instance counts, clustering, failover. That's a deployment diagram's job; putting it here just makes this diagram harder to keep current.
