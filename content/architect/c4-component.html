C4 model

One container opened up: the major structural parts inside a single service and the responsibilities they hold. Unlike a container, a component is never separately deployable — every component inside a container runs in the same process, so it is the container, not the component, that is actually the unit of deployment. Worth drawing only for a service whose internals are genuinely non-obvious — a data-store container or a microservice thin enough to be one component rarely does, and forcing the diagram anyway produces a picture nobody consults again. It sits between the container diagram, which a whole team owns, and the code itself, which one engineer owns, so it is usually drawn by whoever is about to make a change that crosses more than one internal boundary and wants a second opinion before they do. Each component here should map to a real seam in the code — a namespace, a package, an assembly — not an aspirational one; a component diagram that draws boundaries the codebase doesn't actually respect is a wish list, not a picture of the system. It tends to go stale faster than the levels above and below it, because internal refactors that never touch an external contract are exactly the changes nobody remembers to reflect here, so treat any copy older than a couple of sprints as suspect.

Intent

A component diagram answers three questions: what components does this one container break down into, does every component have a home inside some container, and is it clear at a glance how the container actually works.

Structure

Zoom into a single container and draw the components inside it — never the whole system's components on one page, and never more than one container's worth at a time. This is usually what people picture when they're asked for “an architecture diagram”, and confining it to one container at a time is precisely what keeps it from turning into the tangled mess that request usually produces.

As with the container diagram, how much detail you add depends on context — up-front design gets what you know, documentation of an existing system gets the finer implementation details.

Elements

Components are the coarse-grained building blocks living inside a container — in an object-oriented codebase, typically a class or a small cluster of classes behind an interface; in a functional one, a module. For each, capture a name, an implementation technology (plain object, message handler, repository — whatever fits), and a short description of its responsibility.

Three things are worth a deliberate decision rather than an accident:

  • Infrastructure and cross-cutting components. A logging component used by almost everything in the container will clutter the diagram if you draw every connection to it. Options: leave it off entirely if it isn't adding to the story, add a note that says components write logs via it without drawing the lines, or show it unconnected and explain the convention in the key.
  • Shared components and libraries. Include them if they help tell the story, and mark them as shared with a colour or icon if it matters that they're not owned by any one part of the container.
  • Multiple implementations of one component. If a component's implementation is chosen at deployment time — local-disk logging versus a message queue, say — you can draw it once and describe the variability in a sentence, flag it with a colour, or, if you only have one or two swappable components, draw a separate diagram per implementation.

As with the container diagram, it's worth including the people, software systems and other containers this container depends on, with a bounding box around the components to make the zoom level unambiguous.

Interactions

Annotate the purpose of each relationship (“persists data using”, “delegates to”) and, where it matters, whether the call is synchronous or asynchronous. The same discipline that applies at every other level applies here: a line without a label is a line that raises more questions than it answers.

Motivation

A component diagram earns its place on four grounds: it shows the decomposition of a container into distinct responsibilities, it surfaces the dependencies between those responsibilities, it gives a high-level summary of the frameworks and libraries actually in use, and — if the components map cleanly onto real namespaces or packages — it becomes a genuinely reliable way to orient someone in a codebase they've never seen.

Audience & required or optional

Technical people within the development team — this level narrows the audience further than the container diagram, since it stops being meaningful to anyone who won't be reading the code. It's also the first level in the model that's explicitly optional. Skip it for data-storage containers, and skip it for anything simple enough — a thin microservice, most of them — that the container diagram already tells the whole story. Consider it for monolithic applications, especially during up-front design, but weigh that against the cost: past a handful of components the diagram gets cluttered fast, and keeping it honest as the code moves under it is real, ongoing work.

Common pitfalls

  • Drawing one for every container as a matter of routine. Most containers, especially anything closer to a single-purpose microservice than a monolith, don't earn one.
  • Boundaries that describe an aspiration rather than the code. A component diagram that draws lines the codebase doesn't actually respect is a wish list wearing an architecture diagram's clothes.
  • Letting it go stale. Refactors that never touch an external contract are exactly the changes nobody remembers to reflect here — treat any copy more than a couple of sprints old as suspect.
